AI Agent 平台开发实习生｜自动驾驶合成数据平台
项目描述
参与自动驾驶合成数据平台的 AI Agent 模块建设。平台通过 Agent 调用场景编辑工具，支持任务配置、片段处理、编辑校验、预览与发布。工作重点包括将原独立 Agent 能力接入主平台，以及完善 Skill 复用、受控执行、执行证据和运行监控。

工作内容
**Agent 平台集成：**参与将原独立 Agent 的控制器、任务管理能力和操作界面接入主平台，在统一入口管理 Agent 配置、模型与编辑器接口、任务模板、任务/子任务、Skills 目录及执行结果；适配 API Key 鉴权、只读权限和历史接口。
**Agent 工作区建设：**参与基于 React、TypeScript、Ant Design 开发任务管理和执行详情页面，展示任务进度、工具调用过程、执行历史、校验结果与产物，并处理异常提示及代理子路径访问问题。
**Skill 与工具目录：**基于 Skill 注册表和编辑器 Schema 提供工具搜索、参数详情、分类选择与参数校验；兼容历史模板配置，区分“目录可见”“模板已选择”与“运行时已授权”。
**可复用 Agent Skill Package：**参与独立技能包的保存、查询和任务绑定能力建设，将可选 Skills、默认参数及编辑器配置组织为可复用配置；应用前校验 Skill 白名单、参数 Schema、任务模板与编辑器匹配关系，对受控测试任务不兼容等情况拒绝绑定。
**模型循环与工具调用治理：**针对重复无进展调用、相同错误循环及 A/B 往返调用，引入止损判断；在工具派发前检查模型轮次、调用次数、单工具额度和运行时限，并记录阻断原因。
**受控执行与执行账本：**针对指定测试任务冻结工具白名单、有效预算及依赖信息；记录 execution、attempt、operation 和 event，追踪工具调用意图、执行结果与拒绝原因；并发冲突、存储失败或外部结果不确定时阻断不安全的自动重试。
**证据与发布安全：**参与图片、校验报告和工具结果的持久化及完整性校验；通过编辑会话版本使修改后的旧预览、旧校验失效，并区分外部发布“已受理”与业务“最终完成”。
**Agent 执行监控看板：**参与汇总 Agent 任务的待执行、运行中、已完成和失败状态，展示已记录的模型 Token 用量、Skill 调用排行及异常原因；遥测仅记录必要的统计与错误信息，不保存提示词、工具参数或完整执行结果。前端结合任务状态事件刷新，并仅在有运行中任务时进行条件轮询。
**测试与回归：**补充接口、运行时及浏览器测试，覆盖鉴权、技能包配置校验、工具授权、预算限制、并发冲突、证据损坏及监控数据展示等场景。
项目成果
将 Agent 配置、任务操作与执行结果查看整合到合成数据主平台，减少独立服务入口带来的使用和维护割裂。
通过可复用 Skill Package 降低相似 Agent 任务重复配置的成本，并在绑定前校验配置兼容性。
通过工具白名单、预算限制和循环止损，增强 Agent 工具调用的可控性。
通过执行账本、证据校验与监控看板，提升任务状态、工具使用和异常原因的可追溯性。
对远端编辑和发布中的结果未知情况采取保守阻断策略，降低盲目重试造成重复副作用的风险。

Q1：Skill Package 和普通任务模板有什么区别？
**A：**任务模板定义任务的整体执行方式；Skill Package 更侧重可复用的 Skill 组合、参数和编辑器绑定。它可以应用到符合条件的任务，但应用前必须重新检查目标任务的模板、编辑器和 Skill 配置，不能因为曾经保存成功就直接信任。

Q2：为什么技能包已经校验过，启动 Agent 时还要再次检查？
**A：**保存后任务模板、编辑器或 Skill 注册内容仍可能变化。启动时再次检查可以避免使用已经失效的配置；同时，配置校验也不能代替受控执行路径的运行时白名单和预算检查。

Q3：监控看板的 Token 数据是如何保证可信的？
**A：*只统计模型接口实际返回并记录的用量，不根据回复文本长度估算。未上报用量时展示“暂无数据”，而不是补一个推测值；这也意味着监控数字代表已记录的执行*，不应被解释为平台全部历史消耗。

Q4：为什么监控系统不保存提示词和工具参数？
**A：**看板要解决的是“任务是否运行、用了多少资源、调用了哪些 Skill、因何失败”，不需要保存完整业务输入。限制遥测字段可以降低敏感信息泄露风险，也避免监控数据与执行账本承担重复职责。

Q5：Agent 一直调用同一个工具时，你们如何处理？
**A：**结合工具名、参数、已知状态和返回结果判断是否持续无进展，同时识别相同错误及 A/B 往返。正常的 pending 等待不会直接被判为死循环，但仍受总轮次、工具额度和 deadline 限制。

Q6：外部发布接口超时后，为什么不能立即重试？
**A：**本端超时不代表远端没有受理。直接重试可能重复发布，因此需要保留已发送意图，将结果标为待核对；在确认外部事实之前，不把未知状态当作失败或成功。

Q7：你如何区分“Agent 执行完成”和“业务完成”？
A：模型循环结束、工具执行成功、外部发布受理和最终业务完成是不同阶段。比如获得 workflow ID 只能证明外部系统受理了请求，不能证明后续渲染、质检已经成功。


一、项目与 Agent 架构
1. 请用一分钟介绍你做的 Agent 项目。
我参与的是自动驾驶合成数据平台中的 Agent 模块。Agent 会根据任务调用 Skill 和场景编辑工具，完成片段处理、编辑、校验、预览等步骤。我的工作主要围绕三件事：把 Agent 能力接入主平台、约束模型的工具执行，以及让执行状态和异常能够被追踪。

2. 这个项目和普通的大模型聊天应用有什么区别？
普通聊天应用主要处理一问一答；这里的 Agent 会调用工具，部分工具还会修改场景或触发外部发布。模型说“完成了”不能作为业务完成的依据。系统必须管理工具权限、执行预算、外部副作用和最终结果核对。

3. 为什么要把原独立 Agent 服务接入主平台？
独立入口会让登录权限、任务操作和结果查看分散。接入后，用户可以在合成数据平台内配置 Agent、管理任务并查看执行过程。不过接入不只是搬页面，还要处理接口鉴权、任务管理器调用和原有数据、接口的兼容。

4. Agent 接入主平台时，最需要防范什么兼容问题？
我会重点看三类：第一，旧 Agent 接口和主平台统一响应格式是否冲突；第二，旧任务和配置能否继续读取；第三，根路径与代理子路径下的页面、静态资源和 API 是否都能正确访问。不能为了新页面把原有执行链路改坏。

5. Agent 任务为什么适合用异步执行？
模型请求和编辑器调用主要在等待外部 I/O，任务持续时间也可能远大于一次 HTTP 请求。把执行过程放在异步任务中，API 可以先返回运行标识，再由前端查询状态。但异步任务本身不解决持久化和故障恢复，仍需要执行记录与状态核对。

二、Skill 与技能包
6. Skill 和编辑器原子工具有什么区别？
Skill 更像封装好的业务能力，可能在内部组合多个编辑器操作；编辑器原子工具则对应更细粒度的查询或修改接口。因此一次 Skill 调用不一定只产生一次远端操作。做预算和副作用治理时，不能只看模型表面发起了几次 Skill 调用。

7. 为什么 Skill 目录要从注册表生成，而不是前端写死？
注册表才是实际可用 Skill 的来源。前端写死名称和参数，代码更新后很容易出现“页面能选、运行时找不到”或参数不一致的问题。从真实注册信息生成目录，才能让展示内容与实际能力保持一致。

8. 任务模板和 Skill Package 分别解决什么问题？
任务模板描述任务整体如何执行；Skill Package 侧重把一组 Skills、参数配置和编辑器绑定组织成可复用配置。多个相似任务可以复用技能组合，但应用到具体任务前仍需校验模板和编辑器是否匹配。

9. 保存技能包时主要校验哪些内容？
包括技能包名称、Skill 是否在已注册目录中、是否存在重复 Skill、参数是否属于所选 Skill，以及参数值是否符合对应 Schema。还要限制配置规模，并拒绝与目标任务模板、编辑器或受控测试路径不兼容的绑定。

10. 为什么保存成功的技能包，任务启动时还要再次校验？
因为保存后任务绑定的模板、编辑器或可用 Skill 可能发生变化。“保存时合法”不保证“执行时仍合法”。启动前重新检查可以避免使用过期配置，也不能用配置校验取代运行时的工具授权。

11. 为什么模板中 tools 未设置和空数组不能视为相同？
这两种写法可能承载不同的历史语义：未设置通常沿用旧执行器的默认行为，显式空数组则表达用户没有选择工具。如果编辑页面把两者自动互换，旧任务的实际执行行为可能在用户不知情的情况下改变。

三、模型循环与受控执行
12. 模板里已经选择了工具，为什么执行时还要检查白名单？
模板选择是配置，不是强制安全边界。模型仍可能请求未勾选的工具，运行器也可能附加工具。因此受控路径需要在实际派发前检查冻结的白名单；仅在前端隐藏选项，不能证明后端不会执行。

13. LoopGuard 要解决什么问题？
它主要防止模型在没有进展的情况下重复调用工具，例如反复提交同样参数、反复得到相同错误，或在两个无效操作之间来回切换。这类循环会消耗模型和工具资源，若涉及有副作用的工具，还可能放大风险。

14. 如何避免把正常等待误判为死循环？
不能只看工具名重复，还要看参数、已知状态和返回结果。明确的 pending 或 running 状态不直接判为无进展；但等待仍然计入轮次、调用额度和总时限，不能因为“还在等待”就无限运行。

15. Agent 执行预算包括哪些维度？
主要包括模型轮次、工具调用总次数、单工具调用次数和运行时限。它们限制的是不同风险：总次数限制整体消耗，单工具额度防止局部滥用，deadline 防止长时间挂起。真正生效的上限还不能放宽平台已有的限制。

16. 为什么预算和工具权限要在任务启动时冻结？
如果任务执行期间不断读取可修改的模板，运行规则就可能中途变化，事后也难以解释某次工具调用为什么被允许。启动时冻结有效配置，能让本次执行按确定规则运行；之后的模板修改只影响新任务。

17. Agent 请求了一个未授权工具，系统应该怎么处理？
应在调用编辑器或外部系统之前拒绝，并记录工具名及机器可读的拒绝原因。还要给这次模型工具请求形成对应结果，避免模型侧只看到一次“没有回应”的调用，导致上下文和执行记录不一致。

四、账本、证据与故障处理
18. execution、attempt 和 operation 为什么要分开？
execution 表示一次任务运行；attempt 表示其中某个片段或子任务的一次尝试；operation 表示具体工具调用或外部操作。分开后，才能回答“整个任务运行了几次”“哪个片段重试了”“哪次远端操作结果未知”等不同问题。

19. 为什么调用外部工具之前要记录意图？
因为外部调用可能成功，但本地在收到或保存回执前中断。如果事前没有记录，恢复时就无法判断是否曾经发起过这次操作。先记录意图，至少可以在结果不明时保留“可能已发送”的事实，阻止盲目重放。

20. 发布接口超时了，为什么不能直接重试？
本端超时不代表远端没收到请求。直接重试可能造成重复发布。正确做法是保留发布意图，把状态标记为未知或待核对；如果已有明确的受理记录，重复的同一意图也应尽量复用既有结果，而不是再次请求。

21. 为什么再次编辑后，旧预览和旧校验必须失效？
预览和校验只能证明生成它们时的编辑版本。后续修改改变了场景内容，旧证据就不能证明当前内容符合发布要求。通过会话 revision 关联编辑与证据，版本不一致时要求重新校验，可以避免“校验的是旧内容，发布的是新内容”。

22. 图片已经保存了，为什么还要校验文件大小和哈希？
保存过不代表读取时仍然完整。文件可能丢失、被覆盖或损坏。大小和哈希校验让执行记录中的证据引用可以被核实；校验失败时应展示缺失或损坏状态，而不是继续将该结果当作有效成功证据。

23. Agent 所在进程中断后，为什么不自动把任务标记为失败并重跑？
本地进程中断无法证明远端编辑或发布没有发生。如果直接标记失败并重跑，可能重复执行有副作用的操作。因此更安全的是先保留不确定状态，核对已有执行记录和远端事实，再决定是否允许后续操作。

五、监控、测试与项目边界
24. Agent 监控看板的数据如何做到可信且不过度收集？
任务状态从实际任务记录汇总；Token 只统计模型接口已返回的用量，不根据文本长度估算；Skill 排行和异常原因来自已记录的执行事件。看板只需要统计值和必要错误码，不需要保存提示词、工具参数或完整业务数据。没有上报的数据应显示为空，而不是编造一个数值。

25. 你如何证明这些功能有效？有什么尚未验证？
我会用单元测试验证白名单、预算、重复止损和状态判断，用故障注入覆盖存储失败、证据损坏及外部回执未知，再用浏览器测试检查配置、权限和异常展示。与此同时，我会明确区分隔离测试通过与真实模型、编辑器、外部发布及生产部署验收通过；后者不能仅凭前者推断。
