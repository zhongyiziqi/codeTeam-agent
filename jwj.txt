# 后端实习经历简历内容

## 后端开发实习生 | 合成数据标注与自动化处理平台

### 项目描述

参与公司合成数据标注平台后端开发。平台基于 FastAPI、MongoDB、Beanie、Dependency Injector 构建，对接 XLabel、DAP、COS 等内部平台，支持合成数据生成、动态标注、预标注、编辑加工、结果回填等业务流程。

### 工作内容

- 参与合成数据标注后端建设，负责数据处理状态管理、自动化标注链路优化、Workflow 流程修复及外部平台接口对接等工作。
- 设计并实现数据处理状态库模块，基于 MongoDB/Beanie 记录单条数据在动态标注、预标注、编辑加工等阶段的状态、开始时间和完成时间，提供创建、查询、分页筛选、阶段更新、汇总统计等 RESTful API。
- 支持按项目、批次、数据 ID、阶段状态进行数据筛选与统计，帮助业务侧快速定位处理失败、卡住或未完成的数据，提升合成数据处理流程的可观测性。
- 参与 XLabel 自动预标注链路优化，修复 select_dataset_id 被截断、自定义后缀解析异常、预标注模型 ID 配置错误等问题，保证预标注任务能够使用完整数据集 ID 正确发起。
- 参与 DAP 合成数据标注 Workflow 链路改造，修复 Matrix 572、Matrix 860 到交付数据生成的流程衔接问题，完善 revise_label 输入输出与 workflow_result 的数据传递逻辑。
- 优化合成数据提交流程，拆分数据提交与数据集提交边界，避免流程间状态混用，提升合成数据生成、标注修正和交付链路的稳定性。
- 支持自定义合成数据集名称、数据集 ID 后缀保留与解析逻辑，增强 XLabel 数据集创建、复制、curation 和预标注流程的兼容性。
- 优化资产管理接口，实现资产分页接口仅返回各类型最新模型版本，并统一版本号解析规则，提升资产列表展示与模型版本选择的准确性。
- 支持多背景资产批量创建能力，扩展合成数据生成场景，提高批量任务配置效率。
- 为批量上传数据接口增加 interval_seconds 限速参数，默认相邻资产间隔 0.5 秒异步等待，避免批量导入时连续高频写入 MongoDB，降低对 XLabel 主库造成瞬时压力的风险。
- 编写和补充相关单元测试，覆盖 XLabel 数据集 ID 解析、资产版本筛选、合成数据 Workflow 输入输出等关键逻辑。

### 项目成果

- 提升合成数据从生成、动态标注、预标注到交付回填的流程稳定性。
- 增强数据处理链路的可观测性，使业务侧可以按批次和阶段快速定位异常数据。
- 降低自动预标注任务因参数解析、模型配置、数据集 ID 传递导致的失败风险。
- 通过接口级异步限速控制批量资产登记节奏，减少高并发写库对 XLabel 主库稳定性的影响。
- 完善后端服务在多环境部署、长时间运行和数据库连接异常场景下的可靠性。

## 模拟面试问题与参考回答

以下问题按照互联网大厂后端、车企数据平台、自动驾驶数据平台面试中常见的追问方式整理。回答时不要死背，可以按“背景 -> 我做了什么 -> 为什么这样做 -> 结果”的顺序展开。

### 1. 请介绍一下你这段实习主要做了什么？

参考回答：

我实习期间主要参与合成数据标注平台的后端开发。这个平台服务于自动驾驶合成数据生产链路，负责把合成数据从生成、动态标注、预标注、编辑加工到最终回填 XLabel 平台串起来。

我做的工作主要有三类。第一类是数据处理状态管理，我基于 FastAPI、MongoDB 和 Beanie 设计了数据处理状态库，记录每条数据在动态标注、预标注、编辑加工等阶段的状态和时间戳，并提供分页查询、阶段更新和汇总统计接口。第二类是自动化标注链路的问题修复，包括 XLabel 的 select_dataset_id 解析、预标注模型 ID 配置、DAP Workflow 输入输出传递等。第三类是工程稳定性优化，比如给批量资产登记接口增加 interval_seconds 限速参数，避免批量导入时连续高频写 MongoDB，对 XLabel 主库造成压力。

### 2. 你说的数据处理状态库解决了什么问题？

参考回答：

之前数据处理链路比较长，涉及动态标注、预标注、人工或编辑器加工等多个阶段。如果某一批数据卡住，业务侧只能通过日志或外部平台逐个查，定位成本比较高。

我做的数据处理状态库是把每条数据的处理状态沉淀到 MongoDB 中。每条记录用 data_id 作为业务主键，记录 project、batch_id、data_name，以及 stages 字段。stages 里面按阶段保存状态，比如 pending、processing、completed、failed，同时记录 start_time 和 finish_time。这样前端或运营同学可以按批次、项目、阶段状态筛选，也可以看汇总统计，快速知道哪一批数据在哪个阶段失败或等待。

### 3. 为什么 data_id 要做唯一索引？

参考回答：

因为 data_id 是业务侧识别一条数据的主键。一条数据在整个处理流程中应该只有一条状态记录，如果允许重复，会导致同一条数据出现多个状态版本，后续分页、统计和阶段更新都会变得不可信。

所以我在模型里给 data_id 加了唯一索引，同时在创建记录时先查询是否已有记录，如果存在就直接返回已有记录，实现接口幂等。这样即使调用方重复提交，也不会重复创建状态记录。

### 4. 阶段状态为什么设计成 stages 字典，而不是每个阶段一个字段？

参考回答：

主要考虑扩展性和查询表达能力。当前阶段有 dynamic_annotation、prelabel、editor，但后面可能增加质检、回填、重试等阶段。如果每个阶段都设计成固定字段，后续加阶段需要频繁改模型和接口。

使用 stages 字典后，key 是阶段名，value 是阶段详情，结构比较统一。查询时也可以通过类似 stages.prelabel.status 的方式按某个阶段状态过滤。为了兼顾查询性能，我给常用的 batch_id + 阶段状态建立了复合索引。

### 5. 你怎么计算整体状态 summary？

参考回答：

summary 分两层。第一层是 by_stage，按每个阶段统计 pending、processing、completed、failed 的数量。第二层是 overall，给每条数据计算一个整体状态。

整体状态的规则是偏保守的：如果任意阶段 failed，这条数据整体就是 failed；否则如果任意阶段 processing，整体就是 processing；如果所有阶段都是 completed，整体就是 completed；剩下的就是 pending。这样业务侧看到的整体状态更接近真实处理进度，也不会把局部失败的数据误判为成功。

### 6. 如果数据量很大，summary 会不会有性能问题？你会怎么优化？

参考回答：

当前实现适合中小批次的数据处理统计，因为它会按过滤条件把 stages 投影出来后在服务层做统计。如果数据量扩大到几十万或百万级，确实可能有性能问题。

我会从几个方向优化。第一，保证 batch_id、project、deleted 和常用阶段状态字段有索引。第二，把统计逻辑尽量下推到 MongoDB aggregation，用 $group 直接在数据库侧聚合。第三，如果业务频繁看固定批次的统计，可以维护批次级 summary 快照，在阶段状态更新时增量更新。第四，对大批量历史数据做冷热分层，避免每次统计扫描太多历史记录。

### 7. 你提到给批量资产登记接口加了 interval_seconds，为什么要做这个？

参考回答：

这个接口用于批量登记资产，背后会触发多次数据库写入和相关校验。如果一次性连续处理很多资产，请求会短时间内集中打到 MongoDB，尤其 XLabel 那边主库也承载其他业务，可能出现瞬时压力过高，严重时会影响主库稳定性。

所以我给接口增加了 interval_seconds 参数，默认 0.5 秒。批量处理相邻资产时使用异步等待，把连续突发写入变成有节奏的写入。这样既不阻塞整个服务进程，又能降低对数据库和外部平台的瞬时冲击。

### 8. 为什么要用异步等待，而不是 time.sleep？

参考回答：

FastAPI 服务是异步模型，如果在 async 接口里使用 time.sleep，会阻塞事件循环，导致同一个进程里其他请求也被卡住。

异步等待应该使用 asyncio.sleep。它会把当前协程挂起，把事件循环让出来，其他请求仍然可以继续处理。对于限速这种场景，asyncio.sleep 更符合异步 Web 服务的设计。

### 9. interval_seconds 默认 0.5 秒是怎么考虑的？

参考回答：

默认值主要是一个保守的保护参数。它不会让批量任务慢到不可接受，但能明显削平连续写入造成的瞬时峰值。

从工程角度看，这个值最好后续结合实际压测和数据库监控来调整，比如观察批量导入时 MongoDB 的连接数、写入延迟、主库 CPU、慢查询和业务接口错误率。如果数据量更大，也可以把这个参数暴露给调用方，或者做成配置项，在不同环境里使用不同默认值。

### 10. 限速会不会影响用户体验？怎么权衡？

参考回答：

会影响批量任务的总耗时，但这里是典型的吞吐和稳定性的权衡。批量资产登记不是强实时接口，更重要的是稳定完成，不能为了几秒钟的速度把主库打出问题，影响其他在线业务。

所以我更倾向于默认开启轻量限速，同时保留参数让调用方在小批量或测试环境中调整。如果后续对效率要求更高，可以进一步改成后台任务队列，用队列消费速率控制代替请求内串行等待。

### 11. XLabel 的 select_dataset_id 问题具体是什么？你怎么修的？

参考回答：

问题主要是数据集 ID 有自定义后缀时，原来的解析逻辑会把 select_dataset_id 截断，导致传给 XLabel 预标注接口的 ID 不是完整 ID，任务发起失败或找不到正确数据集。

我做的修复是区分不同使用场景。对于需要完整 select_dataset_id 的预标注接口，要原样透传，不能截断。对于需要解析核心数字或后缀的地方，再单独做解析逻辑。这样避免把“展示/搜索用的解析”和“外部接口调用用的真实 ID”混在一起。

### 12. 你怎么判断这是 select_dataset_id 的问题，而不是 XLabel 服务本身的问题？

参考回答：

我会先看失败请求的入参和 XLabel 返回信息，确认实际传过去的 select_dataset_id 是否和数据集真实 ID 一致。然后对比成功和失败的数据集，发现失败场景往往和自定义后缀或 ID 格式有关。

接着我会在服务层补充日志或单元测试，把带后缀的数据集 ID 作为输入，验证原逻辑是否会截断。确认复现后，再调整解析和透传逻辑，并补测试覆盖，避免后续改动再次破坏这个场景。

### 13. 你提到预标注模型 ID 配置错误，这个问题怎么理解？

参考回答：

预标注任务发起时需要传模型 ID，但这里容易混淆两类 ID：一个是本地系统里的 SyntheticModel，也就是 GRE 等合成模型配置；另一个是 XLabel 平台真正用于预标注的模型 ID。

之前有过硬编码或错误使用模型 ID 的问题，导致任务发起失败或者错误难以定位。我做的修复是让调用链使用正确来源的模型 ID，并且在发起失败时把真实失败原因暴露出来，而不是吞掉异常或只返回模糊错误。这样排查成本会低很多。

### 14. Workflow 里 Matrix 572 和 Matrix 860 是什么关系？

参考回答：

从我参与的链路看，Matrix 572 和 Matrix 860 是 DAP 里合成数据标注相关的不同处理节点。572 的输出会作为后续 revise_label 或交付数据构建的一部分，860 负责进一步生成或修正标注结果。

我处理的问题主要是这几个节点之间的输入输出没有完全对齐，比如后续步骤还从旧字段读数据，或者 delivery frames 没有从正确的 workflow_result 里构建。修复后，数据能按照 572 到 860 再到 delivery 的链路正确传递。

### 15. 为什么要拆分数据提交和数据集提交边界？

参考回答：

数据提交和数据集提交虽然都属于合成数据交付链路，但它们的语义不同。数据提交关注单条或多条数据本身的处理结果，数据集提交关注一组数据作为集合的交付状态。

如果两个边界混在一起，容易出现状态串扰，比如单条数据还没处理完，数据集层面就被错误推进，或者反过来数据集状态影响单条数据的处理判断。所以我参与修复时把这两个流程边界拆清楚，让各自读写自己的状态和结果，降低流程间耦合。

### 16. 你写过哪些测试？为什么这些测试重要？

参考回答：

我补充或参与维护的测试主要覆盖几类关键逻辑。第一是 XLabel select_dataset_id 解析和透传，尤其是带自定义后缀的数据集 ID。第二是资产模型版本筛选，确保资产分页接口只返回各类型最新版本。第三是合成数据 Workflow 的输入输出，验证 revise_label 和 delivery 构建能从正确字段读取数据。

这些测试重要是因为它们都属于业务链路的关键分支，一旦出错，表面上可能只是任务失败，但背后会影响整批数据的标注和交付。用测试把这些规则固定下来，可以减少回归风险。

### 17. 如果 POST /asset/sync/json 处理到一半失败，你会怎么保证可恢复？

参考回答：

首先接口需要返回清晰的处理结果，比如 total、success、failed、errors，告诉调用方哪些资产成功、哪些失败。其次单个资产处理最好是幂等的，重复登记同一个资产时不会产生重复脏数据，而是更新或跳过已有记录。

如果批量很大，我会进一步建议把它改造成后台任务：请求只负责创建任务，实际资产登记由任务队列消费，每个资产单独记录状态。这样失败后可以按失败项重试，而不是整个批次从头再来。

### 18. 你觉得这个项目里最有挑战的点是什么？

参考回答：

对我来说最有挑战的是业务链路长，而且依赖多个外部系统。一个预标注失败，可能是本地参数问题、XLabel 数据集 ID 问题、模型 ID 问题、DAP 输出字段问题，也可能是 COS 资源缺失。

所以排查时不能只看报错表面，需要沿着数据流一层层验证：接口入参是什么，本地服务怎么转换，传给外部平台的 payload 是什么，外部平台返回了什么，workflow_result 里是否有后续步骤需要的字段。这个过程让我对后端不仅是写接口，也包括业务建模、链路追踪和稳定性保障有了更深理解。

### 19. 如果让你继续优化这个平台，你会做什么？

参考回答：

我会优先做三件事。第一，把长流程任务进一步任务化和状态化，比如批量资产登记、预标注发起、结果回填都可以有独立任务记录和重试机制。第二，完善可观测性，比如统一 trace_id、关键外部调用日志、失败原因分类和批次级看板。第三，优化数据库查询和统计，对高频查询字段补索引，对大批次 summary 做聚合下推或缓存。

如果从业务角度看，我也会推动把一些容易出错的参数校验前置，比如数据集 ID 格式、模型 ID 是否存在、COS 资源是否可访问，在任务真正发起前就给出明确失败原因。

### 20. 你在这个实习里体现了哪些后端能力？

参考回答：

我觉得主要体现了四方面能力。第一是接口和数据模型设计，比如数据处理状态库的模型、索引、分页和统计接口。第二是异步后端开发能力，比如 FastAPI 异步接口、异步等待限速、外部 HTTP 调用。第三是复杂业务排查能力，比如 XLabel、DAP、COS 多系统之间的数据流问题定位。第四是工程稳定性意识，比如幂等、限速、错误暴露、单元测试和数据库健康检查。

### 21. 车企或自动驾驶数据平台为什么需要合成数据？

参考回答：

自动驾驶模型需要大量覆盖不同场景的数据，但真实数据采集成本高，而且长尾场景很难大量采到，比如特殊天气、复杂路口、危险交互等。合成数据可以用较低成本构造这些场景，补充真实数据不足。

不过合成数据要真正用于训练或评测，需要经过生成、标注、质检、格式转换和平台入库等步骤。我参与的后端平台就是在这个链路里做流程编排和数据流转，保证合成数据能稳定进入标注和交付流程。

### 22. 你怎么理解后端实习生在这种 AI 数据平台里的价值？

参考回答：

AI 数据平台不只是模型训练，背后还有大量数据生产、任务调度、资产管理、标注回填和质量追踪工作。后端的价值是把这些复杂流程系统化、可追踪、可恢复。

我在实习中做的状态库、Workflow 修复、接口限速、ID 解析和测试覆盖，本质上都是让数据链路更稳定、更可观测。对业务来说，稳定的数据链路能减少人工排查和重复处理，也能让模型团队更快拿到可用数据。

### 23. 如果面试官追问“你这个限速是不是太简单了”，怎么回答？

参考回答：

我会承认这是一个轻量级方案，不是最终形态。它的优点是改动小、风险低、能快速缓解批量导入时连续写库的问题，适合当前接口和业务规模。

但如果批量规模继续扩大，更好的方案应该是任务队列加消费速率控制，比如把资产登记拆成异步任务，使用队列控制并发数和 QPS，失败项可以单独重试，同时配合监控动态调整消费速度。所以 interval_seconds 是一个实用的第一步，后续可以演进到更完整的削峰填谷方案。

### 24. 如果面试官问你项目中有没有不足，你怎么说？

参考回答：

我会说目前还有几个可以改进的地方。第一，部分批量操作还在请求链路中串行完成，长远看应该任务化。第二，状态统计目前更适合按批次查询，如果数据规模继续扩大，需要更多聚合优化或缓存。第三，外部平台错误还可以进一步标准化，比如把 XLabel、DAP、COS 的失败原因统一分类，方便前端展示和业务处理。

这些也是我后续希望继续深入的方向：不仅把功能做通，还要把系统做得更稳定、更可观测、更容易运维。

### 25. 请用 STAR 法讲一个你解决线上或准线上问题的经历。

参考回答：

S：合成数据自动预标注链路中，有些任务发起失败，业务侧看到的错误不够明确，影响整批数据处理进度。

R：修复后，预标注任务能够使用正确的数据集 ID 和模型 ID 发起，失败原因也更容易定位，降低了批量数据处理中的人工排查成本。
